# CuraEngine in Docker (no CuraEngine on the host)

Use this when the host that runs `mcp-cura` does not have, and should not have,
CuraEngine installed. The `cura-engine` image contains a fully self-contained
CuraEngine build, so `mcp-cura` talks to it through `docker run` with only the
slice job directory mounted.

Files:

- `docker/cura-engine/Dockerfile` — multi-stage Ubuntu Dockerfile (build stage
  compiles from source, runtime stage is bare `ubuntu:24.04`).
- This document — how to build, wire up profiles, and feed it STLs.

Related: [deployment](deployment.md), [configuration](configuration.md).

## What the image contains

| Stage | Contents |
|---|---|
| `builder` (discarded) | `ubuntu:24.04` + Python 3.12 + Conan 2 + gcc/cmake/ninja/make; clones CuraEngine from the pinned tag and builds `conan-release` |
| runtime | `ubuntu:24.04` + the `CuraEngine` binary + its shared-library closure copied out of the build's `ldd` |

Pinned versions (override with `--build-arg`):

- CuraEngine `5.14.0`
- Conan `2.34.0`
- Ubuntu `24.04` (noble) — Python 3.12, gcc/g++ 13, CMake 3.28, Ninja, make.
  glibc means the prebuilt binaries Conan downloads (its cmake tool) run
  natively; no musl shims are needed.

Nothing else is installed: no compilers, no Python, no network at slicing time.
The image has no `ENTRYPOINT` on purpose: `mcp-cura` invokes it as
`docker run <image> CuraEngine slice ...`, so the first argument is the command.

## Build it

```bash
docker build -t cura-engine:5.14.0 -f docker/cura-engine/Dockerfile docker/cura-engine
```

Smoke test the image:

```bash
docker run --rm cura-engine:5.14.0            # default command prints help
docker run --rm cura-engine:5.14.0 CuraEngine help
```

## How mcp-cura uses it

Set the engine runner to `docker` and point it at the image. With `mcp-cura`
installed on the host, slicing one artifact looks like this:

```bash
export MCP_CURA_ENGINE_RUNNER=docker
export MCP_CURA_DOCKER_IMAGE=cura-engine:5.14.0
export MCP_CURA_ENGINE_DEFINITIONS=/home/you/cura-resources/definitions

mcp-cura doctor
mcp-cura serve
```

Or in `mcp-cura.toml`:

```toml
[engine]
runner = "docker"
docker_image = "cura-engine:5.14.0"
# Point at the folder that directly contains the .def.json files:
search_paths = ["/home/you/cura-resources/definitions"]
```

Important: CuraEngine looks up definitions non-recursively as
`<search path>/<definition-id>.def.json` (see `findDefinitionFile` in its
sources), so every directory you list must directly contain the `.def.json`
files it should resolve, including the parents of your custom definitions
(e.g. `fdmprinter.def.json`, `fdmextruder.def.json`). If you mount the
`resources` root instead of `resources/definitions`, nothing will resolve.

When a slice job runs, `mcp-cura` mounts only the slice job directory at
`/work` and mounts every configured `engine.search_paths` directory
**read-only** at `/cura-defs/0...N`, then passes container-side
`-d /cura-defs/<n>` flags to CuraEngine (and copies the job's `.def.json` and
resolved settings JSON into `/work`). No STLs, profiles, or G-code need to
exist anywhere except your normal `mcp-cura` workspace.

(Older mcp-cura releases silently dropped `search_paths` in Docker mode. The
current code forwards them; keep `mcp-cura` up to date.)

### Direct engine invocation (outside mcp-cura)

Useful to smoke-test the image itself. An arbitrary `.stl` plus a definition
path (or search path) is all CuraEngine needs; `-r` is only for resolved
settings and is generated by `mcp-cura` — omit it when slicing standalone:

```bash
mkdir -p /tmp/job && cp model_0.stl /tmp/job/

docker run --rm \
  -v /tmp/job:/work -w /work \
  -v /home/you/cura-resources/definitions:/cura-defs/0:ro \
  cura-engine:5.14.0 CuraEngine slice \
    -j /cura-defs/0/creality_ender3.def.json -l model_0.stl \
    -d /cura-defs/0 -o output.gcode

# /tmp/job/output.gcode is your G-code
```

## STLs

No shared STL folder is required. `cura_artifact_import` copies (or hash-links)
the mesh into the workspace blob store, and the slice job copies it into the
job directory itself (`<workspace>/jobs/<job_id>/`), which is mounted at
`/work`. The engine only ever sees `/work`, so STLs never touch the engine
image. The only output the engine writes is `/work/output.gcode`, which
`mcp-cura` imports back as a `workspace` artifact on completion.

If you generate STLs outside `mcp-cura` (e.g. another pipeline), import them
first with `cura_artifact_import` — that is the bridge, not a filesystem
mount.

## Custom profiles

CuraEngine needs the full machine-definition inheritance chain
(`.def.json` parents, materials, extruder definitions) or it fails at `-j`.
There is no way around that; the choice is *how* to supply it:

**Recommended: read-only bind mounts (used above).** Keep your profiles on the
host anywhere, list those directories in `engine.search_paths` /
`MCP_CURA_ENGINE_DEFINITIONS`, and mcp-cura mounts them into the engine. Works
for both custom and stock definitions.

**Optional: bake profiles into the image.** Extend the runtime stage with your
own profile folder, e.g. add to `docker/cura-engine/Dockerfile`:

```dockerfile
COPY profiles/ /opt/cura-resources/
```

(for that, change the build context accordingly.) You still need `-d` passed,
i.e. set `engine.search_paths = ["/opt/cura-resources"]`. This makes the image
self-contained but couples an engine version to your printer setup; prefer
mounts unless you are shipping one fixed machine image to a one-off job.

**Stock definitions.** The CuraEngine repo does not ship machine definitions.
Use a shallow clone of `https://github.com/Ultimaker/Cura`'s
`resources/definitions/` (sparse-checkout works well) on the host and mount it
exactly like custom profiles.

## docker-outside-docker caveat

mcp-cura launches the engine with your local docker socket. The engine image
is a child container, so:

- Profile mounts and job dirs must be reachable by the **same docker daemon /
  host** mcp-cura was started on — bind-mounting `/home/...` from a
  docker-in-docker context will not see your host's home directory.
- mcp-cura running inside a container needs `/var/run/docker.sock` mounted and
  profile paths that exist **inside that container at the same path**, or set
  `engine.docker_args` to re-mount them. Simplest: run mcp-cura on the host,
  engine in Docker — this is the supported topology for this image.

## Hardening options

`engine.docker_args` accepts extra `docker run` flags before the image name,
for example:

```toml
[engine]
docker_args = ["--security-opt", "no-new-privileges", "--memory", "2g", "--cpus", "4"]
```

Profile mounts are always passed `:ro` by mcp-cura; keep it that way.

## Troubleshooting

- **`doctor` says image not present.** The image is not pulled over the
  network automatically; build/pull it once. `doctor` reports it as missing
  until the first `docker run` or `docker pull`.
- **Missing `key` / `inherit` errors from CuraEngine.** An inherited
  `.def.json` or extruder definition was not found. Look at your search paths
  — CuraEngine searches them non-recursively for
  `<definition-id>.def.json`, so the directory *containing* the files (e.g.
  `.../definitions/`) must be what you pass in
  `MCP_CURA_ENGINE_DEFINITIONS`, not its parent. The engine error names the
  missing definition id exactly.
- **`CMake 3.26 or higher is required. You are running version 3.25.1`.**
  `foonathan-lexy` (an engine dependency) declares an unpinned
  `cmake/[>=3.18 <4]` tool requirement that Conan resolves to a prebuilt
  3.25.1 — too old for the rest of the graph. The Dockerfile already forces
  `cmake/[>=3.31 <4]` via `[replace_tool_requires]` in the default profile.
  If you build manually on the wiki's path, add the same section to your
  default profile (`conan profile show default`).
- **Build fails at `conan install` with Artifactory/`jfrog` errors.** The
  Ultimaker conan config provides the needed remotes; if a stale
  `artifactory` remote exists on the build host, remove it first:
  `conan remote remove cura` (or override inside the Dockerfile).
- **`CuraEngine` wrote nothing but exited 0.** mcp-cura validates the G-code
  size; if the engine only printed a warning, check `cura_slice_status` logs
  for the engine stderr tail.
- **`permission denied` on `/work`.** The engine runs as root in its container
  but `/work` is the host slice job directory; ensure the host directory is
  readable and the docker daemon can mount it.

## Upgrading

Bump `CURA_ENGINE_VERSION` (and keep `conan==` in sync with upstream's
`required_conan_version`), rebuild, re-tag. Profile paths, mount layout and
mcp-cura config are unchanged across engine minor versions.
